11 — CANON HMI Generation Architecture



Principle

The LLM never emits React, HTML, or SVG source.
The LLM emits a UI specification that names components from a registry and bindings from the machine model.
The renderer is deterministic.

machine semantic
  → component selection (LLM proposes, registry constrains)
    → component schema (Zod/Pydantic)
      → layout (grid / faceplate slots)
        → validator (bindings, ranges, units, commands)
          → approved UI document (revisioned)
            → runtime HMI



Why not Schneider Operator Terminal Expert as the renderer

OTE is the commercial Harmony configuration environment. Catalogs document 650+ objects, compound objects, templates, Web Viewer. Create/edit of compound objects requires Professional Buildtime. There is no public embeddable SDK found that lets CANON generate a native OTE project from JSON.

CANON therefore ships its own industrial HMI runtime and treats Schneider catalogs as Layer A evidence for what an operator screen should contain.

Theming



Dark industrial palette, 4 states: run / idle / warn / fault





Responsiveness



CSS grid faceplates; 16:9 operator, 4:3 optional

Avoid: LLM-written JSX, iframe of a random SCADA, dragging OTE runtime.



Layout algorithm (deterministic)





Group widgets by asset.



Place analog faceplates left, commands right, alarms top.



One primary asset page per request unless the intent names a line overview.



If the validator strips a widget, layout reflows; it does not leave a hole with a guessed tag.



Binding runtime

Each widget subscribes by signalId. The WS payload is {signalId, value, quality, ts}. Quality bad forces the widget into badQuality and disables command buttons on that faceplate.

Command buttons send {commandId} to /api/commands, not a raw node id.
