EXECUTIVE ARCHITECTURE

CANON is not an AI dashboard. It is an engineering product with a hard authority split:

Machine Context  →  Canonical Machine Model  →  AI Intent

Four knowledge layers

Layer A — External engineering knowledge. Schneider catalogs, manuals, software docs, OPC Foundation, IEC/ISA. Stored as evidence records with URL, document number, version, date, product family, and truth status. Never treated as live machine truth.

Layer B — Machine context. What this machine actually contains: PLC identity, tags, I/O, assets, signals, alarms, commands, permissives, runtime values. Sourced from PLC export, OPC UA browse, Modbus map, or a curated demo machine file.

Layer C — CANON engineering model. Normalized entities: Asset, Signal, Controller, I/O, Command, Permissive, Interlock, Alarm, HMIBinding, Dependency, Revision, Evidence, Test. This is the source of truth for generation and validation.

Layer D — AI / generation. Natural language → structured intent JSON. Retrieval over Layer A (and approved Layer C excerpts). Never a source of truth.



1. Why this resource architecture exists

The prototype must demonstrate a closed industrial loop in a hackathon window:





Import machine context



Build the canonical model



Operator request in natural language



LLM structured intent



Retrieved Schneider / standards evidence



Deterministic validation



Dynamic HMI from a component registry



START P401 request



Simulator evaluates permissives



Pump starts; HMI shows RUNNING



Close XV401



START rejected



Change PT401 range 0–10 → 0–16 bar



Change-impact lists affected gauges, alarms, tests, docs



HMI regenerates



Regression tests pass

If any of those steps requires a proprietary Schneider SDK that is account-gated, the prototype must mock that layer and keep the official document as evidence, not as a fake integration.

2.3 Canonical model store

PostgreSQL holds every Layer B/C entity, revisions, evidence pointers, validation results, users/projects. Graph relationships are adjacency tables + recursive CTEs. Vectors live in pgvector in the same database.

2.4 AI stack

Small, curated corpus (hundreds to low thousands of chunks). Hybrid retrieval: tsvector + pgvector. Structured output via JSON Schema. No agent that can write tags.

2.5 HMI engine

A component registry plus JSON UI schema. The LLM emits component specifications, never React source. Runtime binds only to signals that exist in the approved model.

2.6 Control path

Browser
  → CANON API (authn/authz)
    → Command contract lookup
      → Validator (tag, type, permissive presence, role)
        → PLC interface adapter (OPC UA write or Modbus write of *request* coil/register)
          → PLC / simulator evaluates permissives
            → Feedback published on subscription
              → WebSocket → HMI

2.7 Change impact

Every entity has revisionId, content hash, and explicit dependency edges. A range change on PT401 walks edges to gauges, trends, alarms, tests, docs, bindings.



3. What will not be in the prototype





A real Modicon CPU on the bench (optional stretch; simulator is the demo authority).



EcoStruxure Operator Terminal Expert runtime embedded in CANON. That software is licensed, Windows-hosted, and not an embeddable SDK. CANON’s HMI is a separate industrial-style renderer that cites Harmony object categories.



Redistribution of Schneider manuals. Store metadata + extracted facts + citations.



EtherNet/IP or PROFINET stacks.



Neo4j, Milvus, Pinecone, Kafka, Kubernetes.



An unconstrained “chat that controls the plant.”



4. Success criterion

The architecture succeeds if, with the recommended resources, CANON can:





Understand a machine from structured context + cited evidence.



Generate a useful operator HMI from a validated component schema.



Prove bindings against the machine model.



Request actions without the browser talking to the PLC.



Show live feedback.



Survive an engineering change without a stale HMI.

That is the only optimization target.
